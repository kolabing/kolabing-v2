| BE-FX-12 | **`GET /chats` was a hard 500 in production — the chat inbox was dead** (app report, issue #146). BE-FX-8's preview relation was `latestMessage() = hasOne(...)->latestOfMany()`, and `latestOfMany()`/`ofMany()` **always** add `MAX(<primary key>)` to their sub-query (`CanBeOneOfMany::ofMany()` force-inserts the key, whatever column you pass). `chat_messages.id` is a `uuid` and Postgres has no `max(uuid)` → `SQLSTATE[42883] function max(uuid) does not exist`, thrown from `ChatService::visibleCollaborationThreads()` while eager-loading, for **any** viewer with ≥1 thread. `unread-count` survived because it never touches the relation. **CI could not catch it:** `phpunit.xml` runs the whole suite on SQLite, which evaluates `MAX(<uuid>)` happily. Fix: `latestMessage()` is now a plain `->latest('chat_messages.created_at')` (cheap on the lazy path — `HasOne` resolves with `first()`), the three `with('latestMessage')` eager loads are gone, and a new `ChatService::attachLatestMessages()` fills the relation in **two grouped queries** (`MAX(created_at) GROUP BY thread_id`, then fetch those rows) — no N+1, both served by the existing `(thread_id, created_at)` index. Guard test asserts the relation SQL never aggregates the uuid PK (fails on the old definition even on SQLite). Verified read-only against the **production** DB for the reporting business profile: `visibleThreads` 3 threads + resource serialises with real `last_message` previews (was throwing). Branch `fix/chat-latest-message-postgres-max-uuid`. | Fixed in code 2026-08-18 — **needs deploy**; 42/42 chat tests + guard green |

Branch `fix/qa-batch-host-profile-chat-preview-avatars`; app half = kolabing-app PR #108. | Fixed in code 2026-08-02 — pending review + e2e |
